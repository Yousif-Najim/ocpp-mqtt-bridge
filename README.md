# ocpp-mqtt-bridge

A small bridge between EV chargers and an MQTT-based platform. Chargers connect over WebSocket and speak OCPP 1.6-J; the bridge translates their messages into MQTT, and translates MQTT commands back into OCPP messages for the charger.

Built with Node.js 18+, TypeScript (`strict: true`), `ws`, `mqtt` (MQTT.js v5) and Jest.

## How to run it

**Requirements:** Node.js 18 or newer, and Docker (for a local MQTT broker).

```bash
# 1. Install dependencies
npm install

# 2. Start a local MQTT broker (in its own terminal)
docker run --rm -p 1883:1883 eclipse-mosquitto:2 mosquitto -c /mosquitto-no-auth.conf

# 3. Start the bridge
npm run dev                 # runs the TypeScript directly
# or
npm run build && npm start  # compiles to dist/ and runs the JavaScript
```

Chargers connect to `ws://localhost:9000/<chargerId>`.

**Settings** (environment variables, both optional):

| Variable | Default | Meaning |
| --- | --- | --- |
| `PORT` | `9000` | Port the chargers connect to |
| `MQTT_URL` | `mqtt://127.0.0.1:1883` | Address of the MQTT broker |

```bash
PORT=9100 MQTT_URL=mqtt://broker.local:1883 npm start      # macOS / Linux
$env:PORT=9100; $env:MQTT_URL="mqtt://broker.local:1883"; npm start   # Windows PowerShell
```

**Tests:**

```bash
npm test                 # 60 tests
npx jest --coverage      # with a coverage report
npx jest --silent=false  # also show the bridge's log output during tests
```

**Trying it by hand:** connect a pretend charger with `npx wscat -c ws://localhost:9000/charger1` and type OCPP messages, for example `[2,"1","Heartbeat",{}]`. Watch and publish MQTT messages with [MQTT Explorer](https://mqtt-explorer.com/); for example, publish `{"requestId":"r1","payload":{"type":"Soft"}}` to `chargers/charger1/cmd/Reset`, and the charger receives the command.

## Project layout

| File | Job |
| --- | --- |
| `src/index.ts` | Reads the settings and starts everything |
| `src/chargerServer.ts` | The front door: accepts charger connections and keeps a "phone book" of who is connected |
| `src/frames.ts` | Reads incoming OCPP messages (text to a typed message) and builds outgoing ones |
| `src/handlers.ts` | Answers each charger action and publishes to MQTT |
| `src/meterValues.ts` | Translates meter readings into the normalised format |
| `src/commands.ts` | Commands from MQTT to chargers: sending, waiting for the answer, and posting exactly one result |
| `src/mqttClient.ts` | The connection to the MQTT broker |

## Design

**One file per job, with one checkpoint for untrusted data.** Everything a charger sends goes through `parseFrame` first. It is the only place where raw text becomes a typed message: anything that is not valid JSON or not exactly one of the three OCPP shapes is logged and dropped, and the connection stays open. Each action's handler then checks the inside of the payload for that action. MeterValues has two levels of "broken": a broken structure (no connector, no list of entries) rejects the whole message with FormationViolation, while a single bad value is skipped and logged and the rest is still published.

**The front door keeps a phone book of connected chargers.** The charger ID comes from the URL path, and only IDs that are safe in MQTT topics are accepted: a missing ID, or one containing `/`, `+` or `#`, is closed with WebSocket code 1008. If a charger connects again under the same ID, the newest connection wins and the old one is closed, because that almost always means the charger reconnected after a network drop. When a connection closes, it is only removed from the phone book if the phone book still points to it, so a late close of an old connection can't remove the new one. Every connection has an error listener, so a broken WebSocket frame only affects that charger, not the whole bridge.

**Commands use a waiting list that guarantees exactly one result.** Each command sent to a charger gets a message ID generated by the bridge (a UUID, so it can't clash with IDs from the sender or the charger) and a "ticket" on a waiting list, with a 30-second timer. Three things can end a command: the charger's answer, the timer, or the charger disconnecting. Whichever comes first takes the ticket off the list and posts the result; anything that comes later finds no ticket and is only logged. That is how a late answer after a timeout, or a second answer to the same command, never produces a second result. Several commands can be waiting for the same charger, and answers can arrive in any order, because tickets are looked up by message ID. A disconnect only fails the commands of a charger that is really gone, not of one whose old connection closed after a reconnect.

**Testing.** The message logic (`frames.ts`, `handlers.ts`, `meterValues.ts`) is at 100% line and branch coverage, and the command logic (`commands.ts`) is tested with a fake MQTT client, a fake charger connection and Jest's fake clock, so the 30-second timeout is tested instantly. The command logic is kept separate from the MQTT wiring for exactly that reason. Bugs found during development each got a regression test. The live WebSocket server was tested by hand with wscat and MQTT Explorer, and once end to end against a real broker.

**Judgment calls where the case left room:**

- A Heartbeat with extra fields in its payload is accepted (the case only shows `{}`).
- `errorCode` accepts any text; the case asks for a string, not the OCPP list.
- Units other than W, kW, Wh, kWh and A are skipped with a warning, since guessing a conversion could publish wrong numbers. Current without a phase is skipped too, because it can't be placed on a wire.
- An empty `meterValue` list is rejected: there is nothing to publish, and OCPP requires at least one entry.
- Numbers with leading zeros (`"0123"`) are accepted, because their meaning is clear.

## What I left out

- **Pending commands live in memory.** If the bridge restarts, commands that are waiting for an answer never get a result.
- **No offline status for chargers.** When a charger disconnects, its retained status keeps showing the last state.
- **No OCPP subprotocol check** (`ocpp1.6`) and no rule that a charger must send BootNotification first.
- **No authentication or TLS** on the WebSocket.
- **No integration tests for the WebSocket server**; it was tested by hand. The next step would be tests that start the real server on a spare port and connect real clients.
- **kW and kWh conversions are not rounded**, so `1.005` kWh becomes `1004.9999999999999` Wh.
- **Number parsing accepts a few unusual formats**, such as hex (`"0x10"`); a production version would only accept plain decimals.
- **Negative Import values are passed through unchanged**, and if the same measurand appears twice in one entry, the last one wins.
- **Sampled value context and location are ignored.**

## Written questions

**1. Why are info and status retained while meter and command results are not? What would go wrong if commands were retained?**

Info and status describe the current state of a charger, so a service that starts later should get the latest value straight away, which is exactly what a retained message does. Meter readings and command results are events: an old reading or an old result handed to a new subscriber would be misleading. If commands were retained, the broker would replay the last command every time the bridge connected or restarted, so for example an old Reset would reset the charger again. That is why the bridge ignores retained commands.

**2. Which QoS did you choose for status, meter and command results, and why?**

QoS 1 for all three. Status must not get lost, and a duplicate is harmless because it is the same state again. Command results must not get lost either, because a lost result leaves the sender waiting; a duplicate can be recognised by its `requestId`. For meter readings I also chose QoS 1, so no reading is lost; QoS 0 would be defensible too, because readings come regularly and `energyWh` is a running total, so a lost reading loses no energy. The command subscription also uses QoS 1, so commands don't get lost on the way to the bridge.

**3. How did you type the three OCPP frame shapes, and where does unvalidated data become typed data in your code?**

As three types, `Call`, `CallResult` and `CallError`, each with a `type` label, combined into `Frame = Call | CallResult | CallError`. The label lets TypeScript know which fields exist after a check like `frame.type === "CALL"`. Unvalidated data becomes typed data in one place: `parseFrame` in `frames.ts`. Everything going in is `unknown`, and only what passes every check comes out as a typed `Frame`; anything else returns `null`. The payload inside stays `Record<string, unknown>` (checked to be an object, but not its contents) until each handler checks the fields for its own action. Lists from `Array.isArray` are put back to `unknown[]`, so TypeScript keeps forcing those checks.
